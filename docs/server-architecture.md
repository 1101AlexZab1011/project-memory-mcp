# Server Architecture (0.4.0)

## Purpose

Move project memory from per-repository JSON files to a single shared service, so that a
store can hold hundreds of thousands of memories and be reached from any device on a local
network by any agent.

This replaces the file backend rather than sitting beside it.

## Why the file backend runs out

Measured on a real 82-memory store: **49 KB of RAM per memory** — 15 KB for the parsed JSON,
34 KB for the BM25 index and graph. Everything is loaded and held.

| Memories | RAM | |
|---|---|---|
| 10,000 | 480 MB | workable |
| 100,000 | 4.7 GB | exceeds practical RAM |
| 300,000 | 14 GB | no |
| 3,000,000 | 140 GB | no |

The ceiling is roughly 20–30k and it is architectural, not a tuning problem: optimizing BM25
postings or PageRank iterations changes speed, not the requirement to hold the store in
memory. Three other limits arrive around the same point — git degrades badly past ~100k files
in a repository, a single directory with that many entries is slow on most filesystems, and
the `scandir` cache check reaches a full second at 300k.

## Decisions taken

- **Database only.** The file backend is removed, not kept as an option.
- **One server, many projects.** Every request is scoped to a project.
- **Shared static token** for authentication.
- **Memories leave git.** See "What replaces git" below.

## Architecture

```text
   host machine                          any device on the LAN
  ┌──────────────────────────┐          ┌────────────────────────┐
  │ project-memory-mcp serve │          │ Claude Code / Codex    │
  │   --http --port 8765     │◀───MCP───│  .mcp.json ->          │
  │                          │   over   │   http://host:8765/mcp │
  │  ┌────────────────────┐  │   HTTP   └────────────────────────┘
  │  │ SQLite (WAL)       │  │
  │  │  + FTS5            │  │          ┌────────────────────────┐
  │  └────────────────────┘  │◀─────────│ browser: management UI │
  │  web UI on :8765/        │          └────────────────────────┘
  └──────────────────────────┘
```

The MCP server itself becomes the network service. There is no second protocol between an MCP
client and a database: the ten existing tools already are the query API, and MCP defines an
HTTP transport, which Claude Code already supports (`"type": "http"` in `.mcp.json`).

SQLite stays embedded in the server process and is only ever opened from local disk. It must
never be placed on a network share — its locking is documented to corrupt there, which is the
failure mode that would otherwise tempt someone to "just put the file on the NAS".

WAL mode gives concurrent readers with a single writer, which matches the access pattern:
many agents reading, occasional writes.

## Authentication

A shared static token, sent as `Authorization: Bearer <token>`, checked on every request.

- Generated by `project-memory-mcp server init`, stored in the server's config file.
- The server binds to an explicit interface, defaulting to loopback. Serving the LAN is an
  opt-in flag, not the default.
- Requests without a valid token get 401 with no store details in the body.

A LAN is not a trust boundary — it contains phones, printers, TVs, and whatever else joined
the wifi. The store holds file paths, architecture notes, build procedures, and whatever
people save despite the guidance against secrets. An unauthenticated endpoint that answers
`recall` and `delete_memory` is not acceptable, so the token ships in the first version.

Not in scope: TLS, per-user accounts, audit of who wrote what. Single-tenant trusted LAN is
the assumed deployment.

## Schema

```sql
projects(id PK, name, created)

memories(
  id, project_id, status, description, created, last_validated,
  created_from_task, area, body JSON,
  PRIMARY KEY (project_id, id)
)

memories_fts(rowid, search_text)            -- FTS5, external content
labels(project_id, memory_id, label)        -- indexed both directions
tags(project_id, memory_id, tag)
triggers(project_id, memory_id, trigger)
files(project_id, memory_id, path)
label_registry(project_id, label, description)

edges(project_id, src, dst, kind, reason, weight, origin)   -- curated + derived
usage(project_id, memory_id, surfaced, applied, last_surfaced, last_applied)
revisions(project_id, memory_id, revised_at, body JSON)     -- replaces git history
meta(key, value)                                            -- schema version
```

`body JSON` holds the whole memory, so `get_memory` is one row read and adding a field does
not require a migration. The extracted columns exist for filtering, sorting, and joins.

## Ranking at scale

Three signals, same as today, but none of them may load the store.

**Text — FTS5.** BM25 is implemented in C, on disk, incrementally maintained. This removes the
34 KB/memory index from RAM and is faster than the Python implementation it replaces.

The camelCase behavior is preserved by moving it from query time to write time: `search_text`
stores both the original identifier and its split forms, so `bReplicates` is found by
`replicated` and by its exact name. Today's tokenizer runs on insert instead of on every
index build.

**Graph — bounded local walk.** Personalized PageRank currently iterates over every node on
every query. At 3k memories that is 145 ms; at 300k it is impossible.

The walk's mass concentrates within two or three hops of the seeds — the rest of the graph
contributes essentially nothing to the result. So: expand from the seeds to a bounded frontier
(depth 3, or 2,000 nodes, whichever comes first), then iterate on that subgraph alone.

Cost becomes independent of store size and bounded by `K^depth`. With derived edges already
capped at 10 neighbours per memory, depth 3 touches ~1,000 nodes whether the store holds 30k
or 3M. This is also strictly less wasteful than the current behavior, which spends almost all
of its work on nodes that finish with a score of zero.

**Derived edges — materialized on write.** Today they are recomputed for all pairs whenever
the cache rebuilds. On insert, find the new memory's top-K similar with one FTS + label query
and store those edges: O(K) per write instead of O(N²) per rebuild.

**Labels** — an indexed join; label expressions compile to SQL.

## What replaces git

| Property lost | Replacement |
|---|---|
| Distributed backup (every clone held the store) | Scheduled `export` to a JSON snapshot; **must** be configured, not optional |
| `git log` on a memory | `revisions` table — queryable, unlike a diff |
| Code review of memories | Management web UI |
| Memories travel with a clone | Nothing. A fresh checkout has no memories and is pointed at the server |

The redundancy loss is the one that bites. Today every clone is a full backup; after this
change a single unbacked server failure loses everything. Export scheduling is part of the
first version.

What remains in a project repository is `.mcp.json` naming the server and the project id.
`.project-memory/` disappears, `labels.json` included.

## Management UI

Served by the same process at `/`. Browse, full-text search, filter by label/status/date,
edit, delete, inspect a memory's neighbourhood, and run audit views.

This is the piece with no equivalent today. At 82 memories a human can read the directory; at
300k the store is only governable through an interface. Without it, nobody can answer "what
is actually in here" except by asking an agent.

## Migration

`project-memory-mcp migrate --from <path-to-.project-memory> --project <name>` reads an
existing file store into the database and leaves the files untouched, so nothing is destroyed
and the move is reversible by discarding the database.

## Risks

- **Single point of failure.** Server down, or laptop off the LAN, means the agent works
  blind. The skills already degrade gracefully when recall returns nothing, but the failure is
  silent — an agent that cannot reach memory looks identical to one whose store is empty. The
  server should make unreachability explicit in its error, and the skills should say what to do
  when they see it.
- **Unbacked loss.** Covered above; export scheduling is mandatory.
- **Operational burden.** This turns "pip install and go" into "run a service, keep it
  running, manage a token". That is the right trade for multi-device and 300k memories, and the
  wrong one for a single repository with a hundred. The file backend is being removed, so that
  trade is no longer optional — worth being deliberate about.
- **Silent project mix-up.** One server holding many projects means a misconfigured project id
  returns another project's memories rather than an error. Project ids should be validated
  against the registry and an unknown one must fail loudly.

## Phases

1. **SQLite backend** behind the existing store interface; all ten tools green against it;
   `migrate` from a file store.
2. **FTS5 + bounded local walk** replacing the in-RAM index and full PageRank.
3. **HTTP transport + token auth + project scoping.**
4. **Export/backup scheduling.**
5. **Management UI.**
6. **Audit views** over drift, orphans, duplicates, and the surfaced/applied gap.

Phases 1–2 are testable locally with no server involved, which keeps the risky storage change
separate from the risky transport change.
